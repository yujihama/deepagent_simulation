# Agent Simulation PoC 現状報告

作成日: 2026-05-28

## 1. エグゼクティブサマリー

Agent Simulation PoCでは、社員や関係者を1人/1役割ごとの独立DeepAgentとして起動し、相互コミュニケーションの中で業務判断を観察する基盤を構築した。

現時点では、営業社員Aが100万円超の案件を営業部長承認で正しく申請するか、また100万円以下へ分割して課長承認に逃がさないかを題材に、申請承認シナリオを動かせる状態になっている。

これまでの検証から、単なる納期プレッシャーだけでは分割申請は起きにくい一方、発注書・納品物・納品タイミングが自然に分かれる情報や、申請単位に関する曖昧なマニュアルがあると、分割や部分申請が発生しやすいことが確認できた。また、モデルによって逸脱の出方が異なることも確認した。

## 2. プラットフォームの現状

### 2.1 実装済みの主要機能

現在のプラットフォームは、ローカルMVPとして以下を備えている。

| 項目 | 現状 |
| --- | --- |
| フロントエンド | React/Viteによる日本語ダッシュボード |
| バックエンド | FastAPI + SQLite |
| Agent実行 | LangChain DeepAgentを利用したLive実行、APIキー未設定時のモック実行 |
| 初期agent | 営業社員A、営業社員B、営業課長、営業部長、取引先A、ERP Agent、監査Agent |
| Agent設定 | 名前、役割、ペルソナ、参照ドキュメント、利用toolをUIから編集可能 |
| ナレッジ設定 | 規定、ERPチェック仕様書、営業マニュアル、監査観点をUIから編集可能 |
| シナリオ設定 | 初動agentへの指示をUIから確認・編集可能 |
| 実行ストリーム | agent間メッセージ、ERP処理、承認、監査イベントを時系列表示 |
| 実行履歴 | 過去runを選択して、ログ・申請・監査結果を再確認可能 |
| 監査 | 分割疑義、承認者指定誤り、名目調整、後日分割、多重申請などを完了後に評価 |

### 2.2 Agent設計

初期agentは7体で、いずれも同じ基本仕様で起動する。営業社員Aだけを固定ロジックで動かすのではなく、役割、ペルソナ、参照ドキュメント、許可toolによって挙動差を作る。

| Agent | 役割 |
| --- | --- |
| 営業社員A | 観察対象。納期プレッシャー下で正しい申請判断をするかを見る。 |
| 営業社員B | Aの相談相手。助言により判断がどう変わるかを見る。 |
| 営業課長 | 100万円以下の承認者。 |
| 営業部長 | 100万円超の承認者。 |
| 取引先A | 外部関係者として依頼や納期プレッシャーを出す。 |
| ERP Agent | 申請単体の金額に応じて承認ルートを返す。 |
| 監査Agent | 完了後にログと申請履歴を評価する。 |

同じrun内では、各agentがセッション履歴を保持する。たとえば営業社員Aが営業社員Bへ相談し、その後ふたたびBへ相談した場合、Bは過去の相談内容を踏まえて応答する。

### 2.3 ERP Agentと監査Agentの分離

PoCでは、ERP Agentは現実のERPロジックを固定実装するのではなく、ERPチェック仕様書を読んで振る舞うagentとして扱っている。ただし責務は意図的に限定している。

- ERP Agentは申請単体の金額と指定承認者だけを見る。
- ERP Agentは分割疑義や承認回避を検知しない。
- 分割疑義、承認回避、名目調整、後日分割、多重申請は監査Agentが完了後に評価する。

この分離により、「現場処理は通常どおり流れるが、後段監査で逸脱を検知する」という構造を再現している。

## 3. PoCで実施したこと

### 3.1 初期観察シナリオの構築

申請承認を題材に、以下のケースを構築した。

| シナリオ | 目的 |
| --- | --- |
| 正常申請 | 100万円以下の申請を営業課長承認で進めるか確認する。 |
| 高額一括 | 100万円超の申請を営業部長承認で進めるか確認する。 |
| 分割誘発 | 100万円超の案件を100万円以下へ分割しないか確認する。 |
| 急ぎ依頼 | 急ぎの依頼でも正式な承認ルートを守れるか確認する。 |
| 複数比較 | 複数ケースを連続実行して比較する。 |

分割誘発ケースでは、営業社員Aへ納期制約の背景を保持させ、取引先Aから自然な依頼を送らせる構成にした。ランナーは「分割しろ」とは指示せず、A自身が状況、規定、マニュアル、ペルソナを踏まえて判断する。

### 3.2 分割誘発条件の探索

分割がどのような条件で発生するかを検証するため、15種類のvariantを作成した。

主な操作変数は以下。

- 取引先側の依頼内容
- 発注書や納品物の分かれ方
- 希望納期と手配開始期限
- 営業社員Aのペルソナ
- 営業社員Bの助言傾向
- 申請マニュアルや規定文書の記載
- 緊急承認ルートの有無
- Aが規定文書を参照できるかどうか

検証ハーネスとして、variantごとに一時SQLite DBを作成し、Live DeepAgent実行後に申請数、申請金額、承認ルート、監査フラグを自動集計するスクリプトを追加した。

- [split_inducement_poc.py](../backend/experiments/split_inducement_poc.py)

### 3.3 モデル比較

同じvariantを使い、以下の2モデルで比較した。

- `gpt-4.1-mini`
- `gpt-5.4-mini`

各モデルで、一次検証15 runと、代表6条件を各2回反復した12 runを実施した。合計は各モデル27 run、全体で54 run。

## 4. わかったこと

### 4.1 納期プレッシャー単独では分割は起きにくい

納期が迫っている、部長承認に時間がかかる、課長承認なら早い、といった情報だけでは、分割申請は安定して発生しなかった。

多くのrunでは、120万円を営業部長承認で一括申請した。これは、agentが規定とマニュアルを参照できる場合、承認ルールが一定程度抑止として機能していることを示している。

### 4.2 分割は「実務上もっともらしい分割単位」があると発生しやすい

分割が発生しやすかったのは、以下のような条件がある場合だった。

- 発注書が2通に分かれる。
- 納品物が分かれる。
- 納品タイミングが分かれる。
- 申請マニュアルに、納品単位で申請できるようにも読める曖昧な記載がある。
- Aが規定やマニュアルを参照できない。

つまり、単純に「部長承認を避けたい」という動機だけでなく、「分けても不自然ではない理由」があると、分割申請が現れやすい。

### 4.3 モデルによって逸脱の形が違う

`gpt-4.1-mini` と `gpt-5.4-mini` では、同じ条件でも逸脱の形が異なった。

| モデル | 主な傾向 |
| --- | --- |
| `gpt-4.1-mini` | 100万円以下の2申請を作る明示的な分割が発生しやすい。 |
| `gpt-5.4-mini` | 明示的な2分割は避ける一方、全体120万円のうち60万円・90万円・100万円だけを申請する部分申請が発生した。 |

全体集計は以下。

| Model | Total | Risk系Outcome | 明示的な分割 | 部分申請 | 閾値調整/後日化 | 多重申請 | 一括部長承認 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| `gpt-4.1-mini` | 27 | 11 | 11 | 0 | 0 | 0 | 16 |
| `gpt-5.4-mini` | 27 | 8 | 0 | 5 | 1 | 2 | 19 |

この結果から、監査観点は「分割申請をしたか」だけでは不十分であるとわかった。

### 4.4 監査では部分申請・残額後日・多重申請も見る必要がある

`gpt-5.4-mini` では、全体120万円の話が会話ログにあるにもかかわらず、60万円だけを申請するケースが出た。これは申請履歴だけを見ると、単独の100万円以下申請に見える。

そのため、監査Agentには以下の観点が必要。

- 会話ログ上の総額が100万円超か。
- 申請された金額が総額の一部だけになっていないか。
- 残額、後日、別発注、別名目といった語がないか。
- 同一案件の高額申請が重複していないか。
- 目的名が違っても、同一取引先・同一イベント・同一納期の案件として合算すべきではないか。

### 4.5 緊急部長承認ルートの明記は抑止として有効

緊急時の営業部長承認ルートを規定・マニュアルに明記したケースでは、両モデルとも分割ではなく営業部長承認の一括申請に向かった。

これは、単に禁止を書くよりも、「正式に急ぐための代替経路」を用意することが、承認回避の抑止として有効である可能性を示している。

## 6. 現時点の制約・留意点

### 6.1 まだPoC段階

現在の実装はローカルMVPであり、本番利用を想定した権限管理、監査証跡の完全性、可用性、セキュリティ設計は未実装。

### 6.2 LLM実行は確率的

同じvariantでも結果が揺れる。今回の結果は傾向把握として有用だが、発生率として正式に扱うには、各variantを10回以上反復し、統計的に評価する必要がある。

### 6.3 シナリオは合成データ

現時点の取引先、規定、ERP仕様、営業マニュアルはサンプルであり、実企業の実データではない。実運用に近づけるには、実際の規定や業務フローを反映したシナリオ設計が必要。

### 6.4 ERPは簡略化している

ERP Agentは申請単体の金額と承認者指定だけを見ている。実ERPのワークフロー、権限、差戻し、証跡、マスタ参照、入力制約は再現していない。

## 7. 今後の推奨アクション

### 優先度高

1. 監査ロジックに「高額案件の一部だけ申請」を正式な検知項目として追加する。
2. 残額後日、別発注、別名目、多重申請をUI上でも明確に表示する。
3. 分割が発生しやすい代表variantを10回以上反復し、発生率として整理する。
4. 緊急部長承認ルートなど、抑止策の有無による差分を重点的に検証する。

### 優先度中

1. 実験ハーネスをダッシュボードから起動できるようにする。
2. 実行結果のモデル比較をUIで確認できるようにする。
3. LangGraphの永続backendまたはcheckpointerを導入し、長時間runや再開性を強化する。
4. 申請承認以外のテーマ、たとえば値引き承認、契約レビュー、経費精算へ展開する。

## 8. 関係者向けの説明ポイント

説明時には、以下の順で話すと伝わりやすい。

1. 目的: 社員ごとのDeepAgentを使い、規定逸脱がどの条件で発生するかを観察するPoC。
2. 現状: ダッシュボード、agent設定、ドキュメント設定、シナリオ実行、監査まで一通り動く。
3. 実施: 分割誘発シナリオを15条件、2モデルで検証し、代表条件を反復した。
4. 発見: 納期プレッシャーだけでは分割しにくい。実務上もっともらしい分割単位や曖昧な文書があると逸脱が出る。
5. 重要示唆: モデルによって逸脱の形が違う。分割だけでなく、部分申請、残額後日、多重申請も監査対象にすべき。
6. 次の一手: 監査ロジックの拡張と反復検証、実規定を使ったシナリオ拡張。

## 9. 現状判断

PoCとしては、プラットフォームの基本機能と、分割誘発条件を探索する検証サイクルは成立している。

特に重要なのは、単に「LLM agentが申請する」だけでなく、ペルソナ、規定、マニュアル、外部依頼、相談相手、モデル差分を操作しながら、逸脱の発生条件を比較できる状態になったこと。

次フェーズでは、監査観点の拡張と反復実験を進めることで、より実務的に「どの統制が効くか」「どの条件で逸脱が出るか」を説明できるPoCへ進められる。
